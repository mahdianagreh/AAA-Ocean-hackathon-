## 1 · What this adds

The system today: collect data → AI predicts runoff → warn + render the 3D plume
prediction. This phase adds one more step after the warning: **a recommended
response**, generated by a small swarm of role-specific agents that debate the
specific storm's numbers and converge on one course of action, checked against
evidence before it ships.

```
... → exposure calculated → alert issued → [NEW] response swarm runs in the
background → recommendation appears on the alert once ready
```

Nothing upstream changes. The 3D plume and the alert render exactly as they do
today, immediately — this feature fills in a "Recommended Response" panel that
follows shortly after, never blocks it.

## 2 · Trigger

- **Default gate: `risk_level`.** The swarm only runs automatically when the
  triggering `reef_exposures`/`alerts` row is `high` or `critical`. Lower
  severities don't justify the compute or the noise.
- **Human-in-the-loop override.** An operator can force a run at any risk level,
  including `minimal`/`low`, via an explicit action — this is a deliberate escape
  hatch for "I want to see what it would recommend" or "I disagree with the
  automatic gate for this event." Implemented as a request parameter, not a
  standing config row:

  ```
  POST /api/v1/recommendations/trigger
  {
    "run_id": "sim_01...",
    "min_risk_level_override": "low"   // optional; omitted = use the default gate
  }
  ```

  The override is logged on the resulting `response_recommendations` row
  (`triggered_by: "auto" | "human_override"`, plus who) — an operator overriding
  the gate is itself part of the audit trail, not a silent bypass.

## 3 · Execution model

**Background job.** Triggering returns immediately with a `response_recommendations`
row in `status: "running"`; the swarm executes async. The frontend polls
`GET /api/v1/recommendations/{id}` (Supabase realtime is not in play — see the
persistence note below). Nothing about the alert or the 3D view waits on this.

**As built, 11 Aug — not `reefshield-worker-1`.** `worker/run.py` is still a polling
placeholder with no real queue to claim work from (its own docstring says so). Rather
than build a queue just for this, the swarm runs via FastAPI `BackgroundTasks` inside
the **api** process — same precedent `/plume/simulate` and `/exposure/calculate`
already set (`requirements-api.txt`'s own header comment: "this runs synchronously in
the API process... until then this image carries the stack too"). Move it to the
worker once Nizar's queue is real.

**Persistence — deviates from §7 below, decided with Mahdi 11 Aug before writing any
code.** `api/main.py`'s own docstring: "Nothing here opens a database connection."
`exposure/store.py` established the pattern this follows instead: the swarm writes to
local SQLite (`models/response_recommendations.py`), not Postgres, from the live
request path — so it still works with no network/credentials mid-demo, same reason
exposure runs do. A Postgres copy is a later, separate batch bridge
(`db/loaders/response_recommendations.py`, not yet written, same shape as
`db/loaders/exposure_runs.py`), never written from the trigger endpoint itself. The
four tables in §7 are unchanged in shape — SQLite today, Postgres migration
(`supabase/migrations/20260811090000_response_recommendations.sql`, written, not yet
applied — blocked on the pooler connection string, see §9) for the eventual bridge.

## 4 · Model

**Gemma 4 31B, local.** Consistent with the project's existing stance in
`backend/src/rag/answer.py` — no external API by default, because a generative
model summarizing retrieved facts will paraphrase numbers, which is exactly the
failure this project has spent six phases avoiding. A local model keeps that
property: offline-capable, no key, no per-call cost, no vendor dependency mid-demo.

**Measured 11 Aug 2026** (Apple M4 Max, 48 GB RAM, `gemma4:31b` already pulled
locally via Ollama — 19 GB, no download needed):

| Condition | Total time | Output tokens | Notes |
|---|---:|---:|---|
| Cold load (model not in memory) | ~12.5s | — | one-time, paid once per Ollama keep-alive window |
| Warm, `think: false` | **~3.4s** | ~62 | short structured proposal — this is the per-turn cost for the 5 specialist agents |
| Warm, `think: true` | ~25.8s | ~523 (incl. chain-of-thought) | ~8x slower — worth paying only where reasoning quality matters most |
| 3 concurrent requests, `think: false` | **~7.9s wall-clock** (not ~3×3.4s) | 38-49 each | Ollama serves concurrent calls to the same model without a full linear slowdown |

**Design consequence:** run each round's 5 specialists in **parallel**, not
sequential, with `think: false` — a full round costs ~5-10s wall-clock, not 15-20s.
Reserve `think: true` for the **judge** and the **gaps agent** specifically, where
the extra reasoning is worth ~25s each. Original end-to-end estimate: severity brief
(~4s) + 3 parallel rounds (~15-30s) + judge (~26s) + possible 1 revision round
(~15-30s) + gaps agent (~26s) ≈ **roughly 1-2 minutes total**.

**Corrected, first real end-to-end run, 12 Aug** — that estimate under-shot.
Real specialist turns (2-4 sentences, citing specific brief fields and corpus docs,
not the ~62-token benchmark proposal) run longer per call than the short synthetic
prompts §4 measured, and this run didn't converge early (§6.2's near-duplicate check
never matched — real proposals reword themselves round to round even when the
substance agrees), so all 3 rounds ran. Observed: **~7.5 minutes wall-clock**
(07:09:17 to 07:16:47 UTC), with round 1 alone taking ~87s for 5 parallel `think: false`
calls (not the ~10s benchmark) once calls carry a real severity brief + growing
transcript instead of a one-line prompt. Still comfortably a background job — no
change to the architecture — but "1-2 minutes" is wrong; call it **5-10 minutes**
until measured across more scenarios. This also drove the `think: true` client
timeout fix already noted below (§9).

`/ask`'s citations) — an agent proposing an action with nothing behind it is a
refusal, not a guess, exactly like `REFUSAL` in `rag/answer.py` today.

## 6 · Orchestration

1. Severity brief generated once — shared context, not part of the debate.
2. **Up to 3 rounds.** Within a round, the 5 specialists run **in parallel**
   (measured §4: ~5-10s wall-clock per round vs ~15-20s sequential, on this
   hardware), each seeing the brief + full prior transcript, and proposing or
   critiquing one concrete action. If the same core proposal survives 2
   consecutive rounds unchanged, converge early — don't spend a round for its
   own sake. `think: false` for these turns — they're structured propose/critique,
   not deep reasoning, and the 8x latency cost of thinking mode isn't worth it here.
3. **No convergence by round 3:** take the highest-agreement proposal, mark
   `converged: false` explicitly. Never present a majority view as unanimous
   agreement.
4. **Judge, evidence-grounded, `think: true`.** Built on the existing BM25
   retrieval layer (`backend/src/rag/index.py`), same citation discipline as
   `/ask` — approves, or rejects naming the specific unsupported claim. This is
   the one specialist-adjacent step worth the ~26s reasoning cost (§4). **One**
   revision round back to the agents on rejection, then finalize either way
   (approved, or approved-with-caveat if still contested). No second open-ended
   loop here.
5. **Limitations agent runs only after judge approval, `think: true`** — "what's
   missing / what could fail / what's unverified" ships attached to the
   recommendation, never separately, never omitted. Same reasoning-worth-the-cost
   logic as the judge.

## 7 · Database additions

Extends `data-model.md` (Nizar's schema — proposing the shape here, not
redesigning around him; he owns the actual migration).

```sql
CREATE TABLE response_recommendations (
    id                    text PRIMARY KEY,        -- rec_{ULID}
    run_id                text REFERENCES simulation_runs(id),
    event_id              text REFERENCES events(id),
    triggered_by          text NOT NULL,           -- auto | human_override
    triggered_by_user      text,                    -- set when human_override
    min_risk_level_override text,
    severity_brief        jsonb NOT NULL,
    final_recommendation  text,
    status                text NOT NULL,           -- running|proposed|judge_approved|judge_rejected|finalized
    rounds_used           int,
    converged             boolean,
    model                 text NOT NULL,           -- gemma-4-31b-local
    created_at            timestamptz NOT NULL DEFAULT now(),
    completed_at          timestamptz
);

CREATE TABLE recommendation_turns (      -- full audit trail of the debate
    id                 bigserial PRIMARY KEY,
    recommendation_id  text NOT NULL REFERENCES response_recommendations(id) ON DELETE CASCADE,
    round              int NOT NULL,
    agent_role         text NOT NULL,   -- aseza|marine_science|port_ops|civil_defense|tourism
    content            text NOT NULL,
    evidence_cited     jsonb,           -- which corpus chunks it grounded on
    created_at         timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE recommendation_verdicts (
    id                 bigserial PRIMARY KEY,
    recommendation_id  text NOT NULL REFERENCES response_recommendations(id) ON DELETE CASCADE,
    verdict            text NOT NULL,   -- approved|rejected
    evidence_cited     jsonb,
    reasoning          text NOT NULL,
    created_at         timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE recommendation_gaps (
    id                 bigserial PRIMARY KEY,
    recommendation_id  text NOT NULL REFERENCES response_recommendations(id) ON DELETE CASCADE,
    gap_description    text NOT NULL,
    severity           text,
    created_at         timestamptz NOT NULL DEFAULT now()
);
```

`alerts.recommended_action` (already exists, currently a bare `text` field) gains
a `recommendation_id` FK so an alert links to the full deliberation record instead
of a flat string.
